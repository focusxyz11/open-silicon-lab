# Workflow

How we work on Open Silicon Lab. One idea moves from talk to a picture to code, and each step has its own place.

1. **Discuss in Claude (chat).** Ideas, feedback and decisions start in conversation, in a Claude project that holds `CLAUDE.md`, [STATUS.md](STATUS.md), [ROADMAP.md](ROADMAP.md) and [IDEAS.md](IDEAS.md) as its knowledge. A discussion ends with a decision, or with a task.
2. **Prototype the look before the code** when the question is how something should look or feel. A quick sketch or a throwaway page in the chat is enough to decide; it is never merged as it is.
3. **Write the task down** as a GitHub issue with the *Task* form: what and why, where it lives, what to build on, and how to know it is done. One task, one branch, one pull request. [STATUS.md](STATUS.md) lists the tasks that are ready. A chat filing tasks keeps each one small (one view or lab where it can) and fills both *Touches* (the files or views it will change) and *Size* (small: one view or lab, no shared file, a clear spec; else normal): the nightly build reads them to tell which tasks can be built side by side, and gives a small one a lighter helper.
4. **Build in Claude Code on the web**, with this repository attached, one task per session, on a branch. A short session that starts from the issue and `CLAUDE.md` does better than a long one that has forgotten its start. Labs follow [LABS.md](LABS.md).
5. **Open a pull request** with screenshots on a desktop (1280 px) and a phone (390 px), in dark and light, after the checks in *Before you push* (`CLAUDE.md`). CI runs the tests and the browser smoke test.
6. **Look, then merge to `main`.** GitHub Pages deploys it. Look at the live site; what is wrong becomes an issue (or *Break it*, ⚑ on every screen).
7. **Keep what came before.** A version that is replaced is kept on a named branch first (for example `claude/before-dive-2026-11`).
8. **Update [STATUS.md](STATUS.md)** when a task lands, so the next session starts from where things are.

**`main` is protected by a ruleset** (since 26 November 2026, [DECISIONS.md](DECISIONS.md)): every change arrives by pull request (no approvals needed), the `test` check must be green, the branch must be up to date with `main` before it merges, and nobody can bypass it, the owner and the nightly build included. A direct push to `main` is refused.

Sessions can run side by side when their tasks touch different files. Merge one pull request at a time, then update the other branches. Most work now has files of its own: a lab is its declaration, its lab, its engine, its growers, its stylesheet and its smoke check, each a file named for it ([LABS.md](LABS.md)); a view's styles are its own sheet (`src/styles/<view>.css`, loaded with it by `src/core/styles.js`); a smoke check goes in its section's file (`scripts/smoke/<section>.mjs`). What is still shared, and where sessions meet:

- **Words:** `src/i18n/en/<area>.json`, appended by area (a lab's in `labs.json`, its challenges' names in `core.json`, what it grows in `place.json`), and `AREAS` in `src/core/i18n.js` for a new prefix. Keep both sides' keys.
- **The thirteen:** `src/data/frame.js` (`FILED`, `MARKS`), where everything is filed under the core questions.
- **The labs' list:** `src/data/labs/index.js`, an import and a name at the end of `LABS` for each new lab (a browser cannot list a folder). Keep both lines.
- **The shared sheets:** `src/styles/base.css` (what every screen shares, kept under 60 KB with `hold.css`, the first page's) and `src/styles/frame.css` (the frame), when a change is the frame's or every view's rather than one view's.
- **The shell:** `src/v2/app.js` and `src/v2/game.js` (the loop's own challenges), when the change is to the shell or the loop itself.
- **Rarely:** `src/core/styles.js` (`ORDER`, when a view gets a sheet of its own), and `scripts/smoke.mjs` (`NAMES`, when a section is added; CI's groups, `CI_GROUPS` in `.github/workflows/ci.yml`, name the sections, and only the owner edits them; a new section also needs its files in `scripts/smoke/owners.mjs`).

## The browser smoke test, in sections

`scripts/smoke.mjs` runs the browser smoke test, made of sections, each a file of its own in `scripts/smoke/` that opens its own pages and leans on no other: its default export runs it and `about` says what it covers (what they share, the browsers, the address and the problems found, is `scripts/smoke/shared.mjs`). The labs section plays the loop's own challenges, then each lab's own check, `scripts/smoke/labs/<lab>.mjs`. `npm run test:browser` runs them all, `npm run test:browser -- --only labs,ways` runs the ones named, and `npm run test:browser -- --list` says what each covers. Every run prints how long each section took. Locally, run the sections your change touches; the whole run is too long for a laptop. CI runs the sections a pull request's lane needs ([CI's lanes](#cis-lanes)), in groups side by side (`.github/workflows/ci.yml`), and the one check a pull request waits for, `test`, is green only when the logic and words tests and every group are green. A group that passes only on its second run leaves a warning: make that check steady. A draft pull request is not tested (its `test` is skipped; marking it ready for review starts the run). A push to `main` is not tested again: the ruleset lets in only a branch that is up to date and green, so the commit on `main` is the one that was tested, and it goes straight to the site. The whole suite runs on `main` every night and whenever it is started by hand, as a safety net. The browser Playwright downloads is kept between runs.

## CI's lanes

A pull request is tested by its lane, so a small change waits minutes, not the whole suite. CI's first job, `plan` (`scripts/ci-plan.mjs`), reads the files the pull request changes (its merge into `main`) and sorts them with `scripts/smoke/owners.mjs`:

- **Words:** only `*.md`, `docs/`, `content/`, `community/`, `src/i18n/` or `tests/` changed. The logic and words tests run, and no browser.
- **View:** every file changed belongs to a known view or lab (`OWNERS` in `scripts/smoke/owners.mjs`). The logic and words tests run, and only the smoke sections those files belong to, in the groups that hold them. A lab is its section, `labs`, plus the sections that also play it (`LAB_ALSO`).
- **Core (the default):** anything else: the shell and what every page shares (`src/core/`, `src/v2/app.js`, `src/v2/game.js`, `src/styles/base.css`, `src/styles/frame.css`, …), the smoke test's own `shared.mjs`, `smoke.mjs` and `owners.mjs`, `package.json`, `.github/`, or any file the list does not know. Everything runs. When in doubt, core.

The label `ci:full` puts a pull request in the core lane (adding it starts the run again). `test` stays the one required check: it always reports, and it is green when every part the plan chose passed and every part it left out was skipped. The workflow is never filtered by paths, since a required check that never starts would block the pull request for good. Every run also checks that each script parses (`node --check`). `tests/owners.test.mjs` keeps the list honest: every section is owned and in exactly one of CI's groups, no file given to a view is loaded by the shell on every page, a file imported by another view's file belongs to that view too, and a lab played in another section names it in `LAB_ALSO`.

## The nightly build

Each night open task issues (label `task`) are built in groups, in parallel, each pull request tested by its lane while it is built ([CI's lanes](#cis-lanes)). Then the green pull requests ride one **train** into `main`, leaving it green; the issues are read again and what that train made ready is built as the next wave, on its own train, up to four waves a night.

**Side by side only where the work is independent.** Before grouping, the nightly build lists the files each ready task will change (its *Touches*, else what *Where it lives* names, else the code it names). Two groups run side by side when they share no file except additions to a list (a new lab's import and name, a new smoke section, new words, a new fact). Tasks that change a shared file (the words' `AREAS`, `src/data/frame.js`, the labs' list, `base.css`, `frame.css`, `app.js`, `game.js`, `src/core/`, `scripts/smoke.mjs`) beyond such additions go into one `core` group, built one after another by one helper. When every group of the first wave is independent, it holds up to 8 groups (5 when in doubt); each later wave up to 5. Helpers test light (`npm test`, `node --check`, and at most the one smoke section of the view they changed) and leave the rest to CI's lane. A group of tasks labelled `size:small` is built by a helper on Sonnet; the rest, and the train, on Opus. The night's report starts with what waits for the owner (each `needs-owner` task and how many wait behind it), then each wave and its train, then the night's numbers.

**The train.** Merging one by one made every other pull request re-test after each merge (the ruleset wants a branch up to date), so a night of five waited for some fifteen full runs in a row. Instead, the nightly build makes `claude/train-<date>` from `main`, merges the night's green pull requests into it in order of lowest issue number (resolving conflicts hunk by hunk), and opens one pull request, `Train <date>`, listing each pull request it carries and every `Closes #<n>`, labelled `ci:full`. The whole suite runs once; when `test` is green the train is squash-merged and the pull requests it carried are closed with a link to it. If the train fails, it is halved, and each half tested as a train of its own, until the one pull request that breaks it is found; that one becomes a draft with a comment saying what fails, and every train that passes is merged.

**Dependencies are written, not labelled.** A task that needs another one merged first says so in a line of its own: `Waits for: #299, #302` (the Task form has a field for it). The nightly build reads it and starts the task as soon as every issue named is closed, with no one to unblock it. Tasks that follow each other in the same files go in one group (`group:<name>`), built in order on one branch. The label `priority` puts a task ahead of lower-numbered ones (the owner's highest priority: the next generation of computer architecture). The label `needs-owner` is the only hold: the task waits for the owner's decision or review, and only the owner removes it. Write a task when what it builds on is merged or due that night; later parts stay as a list in their plan. The procedure is the repository skill `.claude/skills/nightly/SKILL.md` (`/nightly` in Claude Code).

## Conventions

- **One world, no lists.** Questions are met where they belong; the core questions are never shown together.
- **Questions, not answers.** A stop gives a question, something true to notice, and what people are trying, never the answer.
- **Every number has a source and a date.** Industry figures go in `src/data/facts.json`.
- **Desktop first where it is richer;** the phone gets a simpler design or less content. No sideways scrolling.
